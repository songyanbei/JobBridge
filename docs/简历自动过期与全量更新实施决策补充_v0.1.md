# 简历自动过期与全量更新实施决策补充 v0.1

## 1. 文档效力

本文是 `docs/简历自动过期与全量更新实施方案_v0.1.md` 的实施约束补充。原方案与本文冲突时，以本文为准；未冲突内容继续按原方案执行。实施基线固定为本地 `main` 提交 `64bbc07917bcff4fb38301c1404059c45d08c409`。

本次交付包含代码、隔离环境测试、CI、只读评审、迁移工具和上线/回退手册。不连接真实预发布或生产，不在真实环境执行迁移、灰度、媒体处置或物理删除。

## 2. 业务契约冻结

- 更新简历只面向 `worker`，入口为 `/更新简历 [ID]` 及精确别名“更新简历”“修改简历”“重新提交简历”。
- 更新从空白草稿收集完整业务字段，不复制旧简历字段，不支持字段级部分更新。
- 更新生成新简历 ID；旧 ID 作为历史保留到所有硬删除门禁满足。
- 多份在线简历必须显式选择，不静默选择最新记录。
- 业务 TTL 默认 30 天，候选 TTL 默认 7 天；激活时起算，不追溯重算历史在线简历。
- 本期不提供用户续期；管理员只可按既有 15/30 天规则延期。
- 生命周期时间统一为 UTC-naive `DATETIME(6)`，同一事务只取一次 `now_utc`。
- 五个开关 `RESUME_LIFECYCLE_V2_ENABLED`、`RESUME_REPLACEMENT_ENABLED`、`RESUME_EXPIRY_CLEANUP_ENABLED`、`RESUME_CANDIDATE_CLEANUP_ENABLED`、`RESUME_HARD_DELETE_ENABLED` 默认全部关闭。

## 3. 阶段归属修正

### 3.1 阶段 1

- 三份可断点对账工具均在阶段 1 完成代码、单元测试和隔离 MySQL/Redis 验证：
  - `backend/scripts/phase11_resume_media_reconcile.py`
  - `backend/scripts/phase11_resume_orphan_target_reconcile.py`
  - `backend/scripts/phase11_resume_deleted_target_backfill.py`
- Phase 11 的 Python 运维脚本统一放在 `backend/scripts`；原方案中的仓库根目录 `scripts/...` 路径全部以此修正。
- 阶段 1 的生产允许范围仅为 `pre_cutover` additive DDL 与配置 seed。生命周期回填、三份 Python 对账、媒体修复和任何清理动作即使代码已完成，也不得在生产运行。
- 阶段 1 的测试环境必须实际执行完整 up/down、崩溃续跑、checksum 漂移、部分 DDL、媒体/孤儿/legacy 软删对账；生产执行边界不因测试通过而扩大。

### 3.2 阶段 2 与 minimum build anchor

- 阶段 1 manifest 中的 minimum build anchor 必须保持 fail-closed 未就绪状态，使任何 `post_cutover` 检查都不能通过。
- 阶段 2 先完成 nullable DTO、兼容双读、无条件生命周期双写、API/worker build 探针和 cutover barrier，并形成已测试的独立代码提交。
- 随后用阶段 2 的第二个元数据提交，将 manifest 的 `minimum_build.build_number`、`build_sha`、capabilities 和受影响 checksum 固定到前一个已测试提交。
- anchor 元数据提交只允许修改发布元数据及其测试期望，必须重新执行 manifest/checksum/build-probe 门禁；任何 `post_cutover` step 之前必须已经提交该 anchor。

### 3.3 阶段 4 与阶段 5

- 通用内部清理 API `ensure_target_cleanup_task()`、`target_cleanup_succeeded()` 及岗位/简历兼容包装前移到阶段 4。
- 阶段 4 的替换激活、管理员下架和用户删除必须能在同一数据库事务内写 Resume 状态、关系状态和目标清理任务。
- 阶段 5 再实现实际清理 worker、推荐写 fence、高频扫描、候选回收和硬删除门禁。
- 面向运营的 cleanup HTTP 查询、重驱和媒体隔离处置接口仍在阶段 6 完成。

## 4. 在线读取与图片追加

所有简历目标读取必须共用在线谓词：`audit_status='passed'`、`deleted_at IS NULL`、`delist_reason IS NULL`、`expires_at > :now_utc`，严格模式再要求 `activated_at IS NOT NULL`。

该谓词必须覆盖初次搜索、推荐翻页、搜索默认条件和“给已有简历追加图片”的目标解析。更新会话中的图片只能进入当前 `operation_id` 的草稿媒体集合，候选落库后绑定新候选 ID；不得使用“最近一份简历”或旧的 attachment target 猜测目标。候选、已过期、已下架、已替换和软删简历均不能作为普通图片追加目标。

## 5. 迁移与回退门禁

- 阶段 0 SQL 预检只负责 JSON 形态和聚合计数，不在 SQL 中复制媒体 URL/object key 规范化逻辑。规范化媒体覆盖、同一简历别名重复、跨实体共享、生命周期缺失以及 NULL-safe owner/entity 绑定异常统一由 `backend/scripts/phase11_resume_preflight_media.py` 直接调用生产 `normalize_storage_reference()` 只读核对。
- 预检和 rollout 查询禁止输出原始 ID、userid、存储引用、规范化 key 或 URL，也禁止以确定性/无密钥的 `SHA2`、`CRC32`、`BIT_XOR` 等方式为这些低熵值生成可枚举摘要；只允许固定字段的聚合计数、revision 和布尔门禁结果。
- 孤儿推荐目标的审批例外只用于记录阻塞原因、责任人和期限，不能使 runner `verify` 返回成功，也不能解除硬删除门禁。
- 最终 verify 要求全部孤儿清理任务 `succeeded`、合法媒体缺失为 0、未处置媒体问题为 0、生命周期异常为 0；两次摘要一致后才可写 `verified`。
- down migration 固定采用“为 NULL 候选恢复非空 legacy TTL 并保留软删候选”的策略。不得提供运行时参数在 down 中物理删除候选，也不得逐行临时选择策略。
- down 必须保留迁移 ledger、down backup 和已导出的审计证据；活动关系、未完成 target/media 清理、未知 schema 形态或摘要漂移均 fail closed。

## 6. 后台 API 与 RBAC

固定接口与最低权限如下：

| 接口 | 权限 | 约束 |
|---|---|---|
| `GET /admin/config/resume-replacement-rollout` | `operator`、`super_admin` | 只返回 revision 和成员计数，不在通用配置页暴露原始 allowlist 或成员摘要 |
| `PUT /admin/config/resume-replacement-rollout` | `super_admin` | 要求期望 revision、变更理由和审计；revision 单调递增 |
| `POST /admin/resumes/replacements/{id}/cancel` | `operator`、`super_admin` | 要求理由、关系版本和逐图加锁；关闭关系并建立清理任务 |
| `POST /admin/resumes/replacements/{id}/retry` | `operator`、`super_admin` | 只允许 `conflict`，重新锁定并复核，不绕过摘要/版本规则 |
| `GET /admin/cleanup/...` | `operator`、`super_admin` | 查询任务、死信和媒体问题；响应不得包含 URL、object key 或 PII |
| `POST /admin/cleanup/.../redrive` | `super_admin` | 每批最多 50 条、每管理员每分钟最多 2 批，要求理由和逐项审计 |
| `POST /admin/cleanup/media-issues/{id}/approve` | `super_admin` | 记录处置动作和理由，不视为已解决 |
| `POST /admin/cleanup/media-issues/{id}/execute` | `super_admin` | 执行人必须与审批人不同；完成后复核才置 `resolved` |

`viewer` 无权访问上述接口。稳定业务原因至少包含 `resume_replacement_disabled`、`replacement_in_progress`、`replacement_conflict`、`recommendation_target_stale` 和 `extension_limit_reached`，不得以自由文本替代机器可判定原因。

## 7. 阶段提交门禁

每个阶段依次由新的开发、测试、评审子智能体完成。开发和测试不得提交；评审只读检查暂存区。发现问题回到原开发子智能体修复，再由原测试和评审子智能体完整复验。

仅当 `git diff --cached --check`、该阶段全量后端测试、所需真实 MySQL/Redis 集成测试、涉及前端时的 lint/unit/build 全绿，且无未解决评审发现时才提交。提交后校验提交树等于已测试暂存区且工作树干净，再进入下一阶段。不自动 push、建 PR 或合并，不重写历史。
