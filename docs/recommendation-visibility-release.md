# 推荐权限与字段可配置化实施完成说明

## 1. 交付概览

本次交付完成推荐搜索权限和结果字段可见性的统一治理，覆盖求职者找岗位、厂家找工人、中介找岗位、中介找工人四条推荐路径，并补齐后台配置、策略历史、审计恢复、运行时安全降级、就绪检查和监控告警。

交付分支：`codex/recommendation-permission-config`

目标分支：`main`

## 2. 产品规则落地

| 场景 | 求职者 | 厂家 | 中介 |
| --- | --- | --- | --- |
| 找岗位 | 允许；严格只展示招聘工厂、岗位、薪资三个字段 | 禁止 | 受账号 `can_search_jobs` 开关控制 |
| 找工人 | 禁止 | 受账号 `can_search_workers` 开关控制 | 受账号 `can_search_workers` 开关控制 |

关键字段规则：

- 求职者岗位结果的三个字段是后端硬上限，后台策略不能扩大。
- 岗位招聘主体优先使用岗位级 `hiring_company`，缺失时可回退发布账号公司，并通过 `hiring_company_source` 标记来源。
- 岗位地址优先使用岗位地址；缺失时允许使用发布方经营地址，并明确标记为岗位地址缺失后的回退来源。
- 联系人和电话支持岗位级覆盖；岗位未填写时回退发布账号信息。
- 工资、地点、福利、工种、性别和年龄均按实际存在性渲染，不生成 `0元/月`、空地点或空工种等占位残留。
- 厂家请求找岗位时在搜索前被拒绝，不访问岗位候选数据。

## 3. 技术实现

### 3.1 统一权限门禁

- 新增统一搜索方向与角色矩阵，消除四条推荐入口各自判断造成的权限漂移。
- 同时校验角色硬权限和账号级搜索开关。
- 权限拒绝不修改搜索会话，不产生候选快照，并返回稳定的业务提示。
- 最终结果投影再次校验角色、场景和策略快照，避免上游遗漏造成字段泄漏。
- 搜索侧灰度判断直接使用共享配置和稳定哈希，不再冷加载意图模块及工种字典，避免数据库异常时无关依赖拖慢搜索回退。

### 3.2 策略快照与安全投影

- 策略保存在 `system_config.visibility.recommendation_fields`，服务端独占管理 `schema_version` 和 `revision`。
- 每次请求只读取一次策略，并将完整策略快照贯穿搜索、排序、渲染及“查看更多”。
- 候选快照只保留 ID；最终回复必须提供显式、匹配当前角色和场景的策略快照。
- 数据库读取失败、策略缺失或策略非法时不复用旧策略，立即使用 `builtin-safe-v1`。
- `builtin-safe-v1` 保留求职者固定三字段，且对厂家和中介关闭电话、联系人、地址等敏感扩展字段。
- 数据库恢复后，下一次请求重新读取数据库策略。

### 3.3 后台配置、并发与审计

- 后台新增推荐可见字段矩阵、敏感字段提示、历史详情和历史恢复界面。
- 管理权限分级：`viewer` 可读取策略和历史；`operator` 可执行校验；仅 `super_admin` 可保存和恢复。
- 保存和恢复使用 `expected_revision` 乐观并发控制，冲突时拒绝覆盖。
- 新增敏感字段必须显式确认。
- 策略历史直接基于完整 `audit_log`，返回可恢复状态、过期时间和剩余可恢复天数。
- 恢复历史版本会复制为更高的新 revision，不倒退当前版本号。
- 迁移脚本为 revision 1 创建幂等 bootstrap 审计记录。

### 3.4 岗位字段及来源

- 岗位模型新增 `hiring_company`、`contact_person`、`phone` 字段。
- 管理后台岗位详情、审核编辑和上传链路支持维护岗位级字段。
- 搜索结果结构化记录招聘主体、地址、联系人和电话的最终来源，再按策略决定是否渲染。

### 3.5 可用性与监控

- `/health` 保留为进程存活检查。
- `/ready` 校验当前策略存在、结构合法，且当前 revision 具有完整成功审计；不满足时返回 HTTP 503。
- 生产 Docker 健康探针使用 `/ready`，避免策略未准备好时接收流量。
- 策略加载失败记录累计指标；连续三次失败触发告警，同原因五分钟内去重。
- TTL 清理保留当前有效策略的审计锚点，历史保留期限覆盖可恢复期限。

### 3.6 管理后台账号编辑修复

- 厂家和中介列表统一使用接口返回的 `external_userid`、`registered_at` 字段。
- 原“详情”入口明确调整为“编辑”。
- 账号抽屉按照后端更新接口的扁平请求结构提交公司、地址及中介搜索权限开关。
- 修复因旧字段名 `userid`、`created_at` 造成的详情无法打开或保存失败。

## 4. 数据库迁移

上线前按顺序执行：

1. `backend/sql/migrations/phase10_001_job_visibility_fields.sql`
2. `backend/sql/migrations/phase10_002_ensure_visibility_config.sql`

两个迁移均支持重复执行：岗位字段存在时跳过；默认策略只在缺失时创建；bootstrap 审计按 revision 幂等写入，不覆盖管理员已经维护的策略。

## 5. 验收覆盖

- 角色与搜索方向权限矩阵。
- 账号搜索开关和权限拒绝提示。
- 求职者严格三字段及敏感字段不可扩展。
- 字段缺失、岗位级覆盖和经营地址回退。
- 策略保存、校验、并发冲突、历史详情与恢复。
- 策略缺失、非法、数据库读取失败和恢复后的重新加载。
- 无策略快照、快照缺失及角色/场景不匹配的最终过滤。
- `/ready` 对策略完整性和审计锚点的 503 门禁。
- 策略加载失败指标、连续失败告警及告警去重。
- 前端 ESLint 与生产构建。
- 实际聊天链路验证厂家搜索“电子厂找工人”能够生成并发送推荐结果。

## 6. 发布与回滚

发布顺序：

1. 备份数据库并在目标 MySQL 版本执行两次迁移演练。
2. 执行生产迁移，确认岗位字段、默认策略和 revision 1 审计锚点存在。
3. 部署后端和管理后台，等待 `/ready` 返回 200 后再接入流量。
4. 分角色验证四条搜索路径及后台策略读取、保存和历史恢复。
5. 观察策略加载失败指标和告警。

应用回滚时可回退代码版本；策略回滚应通过后台历史恢复生成新的 revision，不直接修改数据库历史。若数据库暂时不可用，运行时自动采用 `builtin-safe-v1`，不得通过复用旧策略维持敏感字段展示。

## 7. 不包含在代码交付中的本地测试数据
