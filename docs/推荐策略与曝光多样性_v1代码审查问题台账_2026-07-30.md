## REC-AUDIT-001：v1 的 show_more 评分字段合同不一致，异常后仍消耗候选

| 字段 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | closed |
| 影响方向 | `search_job`、`search_worker` |
| 影响模式 | `on` 下命中 candidate/stable v1 的请求 |
| 触发条件 | 首批展示后仍有有效候选，用户发送“换一批/更多” |

### 用户表现

首批推荐可以正常发送；用户发送“换一批”后收到：

```text
系统繁忙，请稍后再试。
```

这不是实际容量繁忙。内部异常被路由层转换成了通用繁忙文案。

### 根因

`backend/app/services/search_service.py` 写入
`candidate_snapshot.ranking_metadata.candidate_scores[*].score_detail` 时：

- 缺少 `RecommendationScoreDetail` 必填字段 `repeat_adjusted_score`；
- 写入了公共 DTO 禁止的字段 `diversity_penalty`。

`show_more()` 恢复剩余候选时调用
`RecommendationScoreDetail.model_validate(detail)`，稳定触发：

```text
repeat_adjusted_score: Field required
diversity_penalty: Extra inputs are not permitted
```

### 连带影响

1. `show_more()` 在完整构造 DTO 前调用 `record_shown()`。
2. 路由捕获异常并返回普通繁忙回复。
3. turn 末尾仍保存 session，并将 inbound event 标记为 `done`。
4. 用户未看到候选，但对应 ID 已进入 `shown_items`；重复点击会继续吞掉下一批。
5. 失败的分页没有形成 recommendation request、delivery、impression，事实指标缺失。

### 本地实证

- `wm_mock_worker_001` 连续两次“换一批”返回繁忙，剩余候选被全部标记为已展示。
- `wm_mock_worker_002` 一次“换一批”返回繁忙，并提前消耗一页候选。
- 直接使用真实 Redis session 和 MySQL 数据调用 `show_more()`，可稳定复现上述
  Pydantic 校验异常。
- 现有相关单元测试 93 项全部通过，说明当前测试未覆盖
  “真实 v1 candidate_scores + 有效剩余候选”的组合。

### 修复要求

1. 新快照的评分明细必须从单一 DTO/投影函数生成，不允许手写第二份字段清单。
2. 写入 `repeat_adjusted_score`，不得把 `diversity_penalty` 写入公共
   `RecommendationScoreDetail`。
3. 兼容已经存在于 Redis 中的旧格式快照：
   - 忽略非白名单字段；
   - 从顶层 `final_score` 或 `base_score × repeat_factor` 恢复缺失的
     `repeat_adjusted_score`；
   - 对兼容读取打结构化计数，不记录候选正文。
4. 在回复和推荐 DTO 完整构造成功后再提交 `shown_items`；任何异常不得推进分页游标。
5. 补齐岗位/工人、candidate/stable、旧快照兼容、异常不推进状态、推荐事实与曝光闭环测试。

### 验收标准

- 候选数大于 3 时，连续“换一批”可按快照顺序返回剩余候选。
- 返回的 `RecommendationItem.score_detail` 通过严格 DTO 校验。
- 注入 DTO 构造异常后，Redis `shown_items` 和 `session_version` 不发生业务推进。
- 旧格式 Redis 快照在 30 分钟 TTL 内仍可安全分页。
- 每次成功分页形成正确的 show_more request、复用原 served attempt，并生成
  delivery/impression/click attribution 合同。
- 失败分页不产生虚假曝光，也不被统计为成功 recommendation request。

## REC-AUDIT-002：分页及二次检索在结果对象完成前推进 `shown_items`

| 字段 | 内容 |
|---|---|
| 优先级 | P1 |
| 状态 | closed |
| 影响方向 | `search_job`、`search_worker` |
| 影响模式 | v1 `show_more`、确认放宽、自动放宽 |

### 发现

除 REC-AUDIT-001 的严格评分 DTO 异常外，搜索代码还有同一类“先写状态、后做可能失败的构造”的顺序问题：

- `backend/app/services/search_service.py` 的 `show_more()` 在候选有效性校验、权限过滤、推荐 DTO 构造之前调用 `record_shown()`；
- 初次岗位/工人搜索和 `execute_relaxed_search()` 也在格式化回复及推荐项构造之前调用 `record_shown()`。

因此只要后续的权限映射、字段格式化、评分兼容读取或推荐字段拼装抛异常，Worker 仍可能把 session 保存为已推进状态。用户看不到候选，但下一次请求会跳过这些候选；失败 turn 还可能被路由层转换为普通“系统繁忙”回复。

### 验收要求

1. 先在局部副本计算完整回复、推荐项和剩余数，所有 DTO 校验成功后再一次性推进 `shown_items`；
2. 任何异常都不得改变 `shown_items`、快照排序版本或分页游标；
3. 自动/确认放宽路径与 `show_more` 使用相同的事务式状态提交测试；
4. 测试中注入权限过滤异常、格式化异常和评分兼容异常，验证失败后重试仍返回同一候选。

## REC-AUDIT-003：候选删除的 Redis 反查索引只有读取，没有任何写入

| 字段 | 内容 |
|---|---|
| 优先级 | P1（隐私闭环） |
| 状态 | closed |
| 影响范围 | 候选删除、用户删除后的“别人看到过我”清理 |

### 根因

`backend/app/services/recommendation_privacy_service.py` 定义并读取：

- `recommendation:session:delivery:{delivery_id}`
- `recommendation:session:target:{target_type}:{target_id}`

但仓库中没有任何推荐投递、session mutation 或 snapshot 保存路径创建这些 Redis 索引（全仓库搜索只有上述读取/删除代码）。隐私清理因此不能定位其他用户的会话，只能清理 MySQL 中能反查到的 delivery/impression/event/attempt。

即使索引补齐，当前 `_scrub_session_payload()` 也只处理 `candidate_snapshot.candidate_ids` 和 `shown_items`，没有从 Redis snapshot 的 `ranking_metadata.candidate_scores` 删除被删候选的键；被删候选 ID 仍可能留在 Redis。

### 连带影响

- 候选用户删除后，其他用户 Redis session 仍可能保留该岗位/简历的 snapshot、评分细节和 shown 状态；
- 下次 `show_more` 可能继续读取已删除候选，或者因 snapshot 与数据库不一致丢失分页；
- 这违反方案要求的候选删除反查并清理 Redis snapshot/shown_items/评分元数据三处合同。

### 验收要求

1. 每次推荐 session 写入/更新都维护 delivery 与 target 两类反查索引，并设置不长于 session TTL 的过期时间；
2. 清理时按索引定位会话，原子 CAS 重写 session；
3. 同步 scrub `candidate_ids`、`shown_items`、`ranking_metadata.candidate_scores` 及 shadow 排名字段；
4. 索引缺失、Redis 不可用和重复执行均有可观测失败/重试语义，且不得退化为全库 `KEYS` 扫描。

## REC-AUDIT-004：新增 `content_expires_at` 迁移不回填既有 delivery

| 字段 | 内容 |
|---|---|
| 优先级 | P1（隐私/留存） |
| 状态 | closed |
| 影响范围 | 已执行过 `phase9_002` 的环境升级 |

### 根因

`backend/sql/migrations/phase9_005_recommendation_delivery_ttl.sql` 只在缺列时执行：

```sql
ALTER TABLE recommendation_delivery
  ADD COLUMN content_expires_at DATETIME(6) NULL
```

没有按已有 `status/created_at/sent_at` 给历史行回填到期时间。`backend/app/tasks/ttl_cleanup.py` 的正文清理条件要求 `content_expires_at IS NOT NULL`，所以升级前已经存在的 `sent`、`pending`、`unknown` 行在回填前不会进入常规 TTL 清理，密文可能永久保留。

### 验收要求

1. 新增迁移在加列后为历史行回填：`sent/permanent_failed` 按终态时间 + 24 小时，`unknown` 按创建时间 + 7 天，`prepared` 按创建时间 + 24 小时，在途状态按方案上限处理；
2. 回填脚本可重复执行且只补空值，不覆盖已有更短 TTL；
3. 升级后 preflight/verify 必须检查列存在及空值数量，空值只能是明确豁免的历史记录；
4. 用含历史密文的数据库夹具验证清理任务确实能删掉升级前数据。

## REC-AUDIT-005：生产 preflight / migration verify 未检查关键 Phase 9 增量列和完整迁移集合

`backend/scripts/recommendation_preflight.py::check_phase9_applied()` 只检查九张基础表存在、台账中存在至少一条 `phase9%` 记录且没有 `success=0`；它不会确认 `phase9_005`、`phase9_006`、`phase9_007`、`phase9_008` 是否全部成功，也不检查 `content_expires_at`、`client_event_id`、`parent_request_id` 和 shadow 列。

`backend/scripts/apply_phase9_migrations.py` 的 `REQUIRED_COLUMNS`/`REQUIRED_INDEXES` 也没有把 `content_expires_at`、客户端幂等唯一键和 parent 索引列为结构性必检项。因此缺少关键增量迁移时，preflight 仍可能给出 PASS，直到线上请求或 TTL 任务才暴露。

2. verify 增加关键列、唯一键、parent 索引和 shadow 列检查；
3. 增加“台账只有 phase9_001…004、数据库缺 phase9_005”应明确 FAIL 的测试；
4. 对关键增量列的历史回填空值和外键/索引结构给出独立 finding。

## REC-AUDIT-006：shadow 提交后若回复构造异常，运行器状态无法回收

| 字段 | 内容 |
|---|---|
| 优先级 | P1（容量/内存） |
| 状态 | closed |
| 影响范围 | `shadow` 命中请求发生路由异常的故障窗口 |

### 根因

`search_service._submit_shadow_candidate()` 在生成最终 `ReplyMessage` 前提交异步 shadow job。只有 Worker 从最终 replies 中提取到 `recommendation_request.execution_mode == "shadow"` 时，才会在业务事务提交后调用 `activate_persistence()`，失败事务才会按 request ID 调 `discard()`。

如果 shadow 提交成功后，`_post_search_dispatch`、权限映射、DTO 校验或 applier 在返回 replies 前抛异常，路由层会吞掉异常并返回普通系统繁忙回复；此时 replies 中没有 request ID，Worker 无法调用 `discard()`。shadow job 即使完成也会把未激活 state 留在 runner 内存中，重复故障会持续积累。

### 验收要求

1. shadow handle 必须绑定到 turn 生命周期，在任何未提交/未挂载回复的异常出口统一 discard；
2. runner 对“完成但永不激活”的 state 设置有限 TTL/回收扫描并记录计数；
3. 注入 DTO/applier 异常，验证 runner state、队列和 Redis permit/token 最终全部释放；
4. 该故障不得产生 shadow attempt 或错误成本统计。
